# M8.3 — what a 34-genome run costs

**What this is.** The scale measurement ROADMAP's M8.3 asks for ("batch test 10–50+ genomes —
record memory/time limits"), run on the **Điềm corpus**: 34 Iridaceae plastomes, all 150–165 kb,
pinned under `.panel/iridaceae-34/` (PROJECT.md §8.31). Every number below is a measurement on
this machine, taken with `/usr/bin/time -v` and `--force` (the run cache keys on `module_version`,
not on a module's source — H-08 — so a cached run would time a lookup and report a lie).

**The machine, stated once, because a scale number without one is not a number.** Intel
i7-1165G7 @ 2.80 GHz, 6 vCPU visible to WSL2, **8,135,488 kB RAM** (~7.8 GB) with ~4 GB available.
This is an ordinary laptop-class CPU and the memory ceiling the project already recorded in
PROJECT.md §9.14 — the toolkit's stated target, not a workstation.

**How it was run.** One module at a time, `plastid run -m <module> -i <genome …>`, reference first.
Single-genome modules (arity 1) were run once per genome — 34 runs per module — and the table
reports the total for all 34 together with the highest peak RSS seen in any of them. Multi-genome
modules took the reference plus the other 33 in one run.

## The nine single-genome modules, all 34 genomes

| Module | 34 runs, wall clock | Peak RSS |
|---|---|---|
| `genome_stats` | 20.5 s | 87 MB |
| `structure` | 21.6 s | 87 MB |
| `introns` | 21.9 s | 87 MB |
| `ssr` (MISA, vendored) | 25.5 s | 87 MB |
| `codon_usage` | 22.8 s | 87 MB |
| `amino_acid` | 23.9 s | 87 MB |
| `orf` | 12.9 s | 51 MB |
| `gene_table` | 15.3 s | 51 MB |
| `submission` | 12.7 s | 52 MB |

**A whole panel of these is a coffee break, not a batch job** — a quarter of a minute per module
for all 34 genomes, and 87 MB at the worst. The 87 MB is not a coincidence: it is the cost of one
Biopython GenBank parse of a ~300 kB record, and it is the same for every module that reads genes.

## The expensive shape: one whole-genome MAFFT alignment

Three modules align the reference **plus every genome, whole**: `substitutions` (its default
`scope=whole`), `diversity` and `barcodes`. The curve below is **measured on `substitutions`**; the
other two call the same alignment on the same input (module code), which is a reading of the code
rather than a measurement of them — they were not run at 34 in this pass. `substitutions` also has a second scope — `cds`, per-gene — which is the
one the manuscripts quote; both are below, on the same 34 sequences.

| `substitutions` scope | Genomes | Wall clock | Peak RSS | Outcome |
|---|---|---|---|---|
| `whole` (default) | 4 | 1 min 12 s | 91 MB | completed |
| `whole` (default) | 8 | 2 min 44 s | 97 MB | completed |
| `whole` (default) | 16 | — | — | **exceeded 7 minutes**, stopped |
| `whole` (default) | 34 | — | — | **exceeded 11 minutes**, stopped |
| **`cds`** | **34** | **5 min 24 s** | **179 MB** | **completed** |

**The limit here is patience, not RAM.** A whole-genome alignment of 34 plastomes peaks under
100 MB on a machine with 8 GB free — the memory ceiling this project worried about (§9.14) is not
what stops it. What stops it is that MAFFT's progressive alignment over 5.2 Mbp of sequence at this
divergence takes tens of minutes on one core, and its cost grows faster than the genome count: 4 →
8 genomes doubles the time, 8 → 16 more than doubles it again.

**The affordable path is the one the manuscripts already use.** `substitutions --set scope=cds`
returns before the whole alignment is built (module code: `if scope == "cds": return _cds_scope(...)`)
and aligns per gene instead. That is the **CDS-only · shared genes · IR excluded** scope of §6's
golden Ts/Tv, and it is the number the two manuscripts quote. The same 34 genomes, the same module,
the same sequences: **5 min 24 s and it finishes**, against a whole-genome alignment that had not
finished after 11 minutes. It costs more memory than the whole scope (179 MB against 97 MB, because
it holds 79 per-gene alignments) and it is the only one of the two that completes — on a machine
with 8 GB, memory is the cheaper currency.

## What this means for a real run

* **Single-genome work does not need batching.** 34 genomes × 9 modules is under four minutes and
  under 100 MB.
* **A whole-genome alignment is comfortable to 8 genomes and not much past it** (2 min 44 s at 8;
  over 7 minutes at 16). Above that, use the per-gene scope — which is what the comparison tables
  for the manuscripts quote anyway, and which does all 34 in **5 min 24 s**.
* **The corpus is the first dataset that could fail.** Two of its 34 records killed a whole run
  before this measurement was half done (`structure` on a 3 bp trailing window, `orf` on a record
  that annotates `rps16` twice) — PROJECT.md §9.I. Neither shape exists in the data this project
  picked for itself, because it picks records that work.

## Not measured, and why — named rather than estimated

`diversity`, `barcodes`, `popgen` and `synteny` were **not run at N = 34**. The first two align
whole genomes like the curve above; the last two are per-gene and per-pair. None of them has a
number here, and none is inferred from another module's: the honest entry is *not measured*.

What is known about their shape without a finished run is call counts, read from the code and
stated as such: `synteny` calls `nucmer`, `delta-filter` and `show-coords` once per query — 33
times for a 34-genome run — and `kaks` calls MAFFT and `yn00` once per shared gene **per pair**,
about 2,600 of each for this panel. `kaks` is therefore the largest job in the toolkit by tool
calls, and the first number to measure when someone needs it.
